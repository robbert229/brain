# Use Pico CSS for page theming

The landing, sign-in, and failure pages were styled by one hand-written `style.css` (spec 009 research §4), a decision justified there for "a single page." With three server-rendered pages live and the notes UI ahead, hand-rolling the typographic scale, spacing, cards, and buttons stopped paying for itself: the pages drifted from each other and looked it. The daemon now vendors `pico.min.css` (Pico CSS v2.1.1, MIT, license banner inlined; SHA-256 `fbc9a63fc9fc9f72d12fd7fc9806e11fa9f77ae4f9cad146b27003a1119ba3db`) under `/static/`, and `style.css` shrinks to a brand layer: the brain palette via Pico's custom properties, the muted tagline, the alert callout edge, and the skip link. This supersedes spec 009 research §4's rejection of a CSS framework, following the same reasoning as ADR-0010: adopt established libraries for mechanics, keep what is policy. The constraints that shaped the original decision hold — Pico is vendored through `go:embed`, so the binary stays self-contained and offline-capable, the `default-src 'self'` CSP is untouched (no CDN, no fonts, no icons), and the pages remain server-rendered semantic HTML that is complete without scripting (FR-003). Pico was chosen over classless alternatives (water.css, simple.css) for its maintained attribute-driven components (`[role="button"]`, `article` cards) and theming surface of CSS custom properties.
